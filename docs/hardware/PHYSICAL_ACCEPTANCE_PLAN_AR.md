# خطة القبول الفيزيائي الأولى لـExpressLRS TX/RX

هذه الخطة مخصصة لاختبار مرشح البرنامج على أجهزة حقيقية بعد نجاح CI. أداة التسجيل داخل التطبيق لا تفرض ترتيبًا أو قفلًا مرحليًا؛ كل اختبار قابل للتسجيل منذ البداية. الترتيب أدناه موصى به لتقليل المخاطر فقط.

## قواعد الجلسة

- استخدم Candidate SHA واحدًا ثابتًا طوال الجلسة.
- انزع مراوح الدرون قبل أي اختبار RX متصل بمتحكم طيران.
- ثبّت هوائي TX قبل تشغيله أو رفع القدرة.
- أغلق أي برنامج آخر قد يحتجز منفذ COM.
- استخدم كابل بيانات ومصدر طاقة ثابتين.
- لا تسجل UID أو SSID أو كلمة مرور أو Binding phrase في الملاحظات.
- لا تعتبر قبول أمر Bind دليلًا على نجاح رابط RF؛ يلزم دليل مستقل من TX وRX.
- لا تعتبر انتهاء الكتابة نجاحًا قبل Read-back أو تحقق الأداة ثم إعادة الإقلاع وعودة Target والإصدار المتوقعين.

## حزمة الأدلة

من داخل قسم **القبول الفيزيائي وتسجيل النتائج**:

1. اكتب اسمًا مختصرًا للمشغل ومنصة الاختبار.
2. تأكد من Candidate SHA.
3. استخدم **التقاط الحالة الحالية** بعد كل انتقال مهم.
4. سجل لكل اختبار `PASS` أو `FAIL` أو `BLOCKED` أو `SKIPPED`.
5. أضف الدليل النصي والملاحظات.
6. صدّر JSON للاحتفاظ الآلي وMarkdown للمراجعة داخل Pull Request.

يحفظ التطبيق الجلسة محليًا في المتصفح ويستعيدها بعد إعادة التحميل. التصدير ينقح الأنماط الشائعة للبيانات الحساسة.

## المرحلة 1 — تهيئة المنصة

### المتصفح والسياق الآمن

معيار النجاح:

- الصفحة تعمل عبر HTTPS.
- Chrome أو Edge يعرض نافذة Web Serial.
- Candidate SHA ورابط التطبيق والمتصفح مسجلة.

### خط الأساس

سجل:

- اسم TX أو RX المختصر.
- الكابل ومصدر الطاقة.
- وجود هوائي TX.
- نزع المراوح عند وجود متحكم طيران.
- إصدار Firmware الحالي قبل أي تعديل.

## المرحلة 2 — التعريف والاتصال

### TX عبر CRSF

معيار النجاح:

- المنفذ يفتح بسرعة CRSF المباشرة.
- Device Info صحيح وCRC صالح.
- الدور TX مطابق.
- اسم المنتج وإصدار Firmware وHardware وعدد Parameters ظاهرة.

### RX عبر CRSF

نفس المعايير السابقة مع الدور RX.

### المنفذ الخاطئ

اختر منفذ Joystick أو منفذًا لا يرسل CRSF. معيار النجاح هو فشل منظم بلا هوية جهاز وبلا بقاء المنفذ محجوزًا.

### الدور الخاطئ

اختر RX لجهاز TX أو العكس. معيار النجاح هو رفض الجلسة وإغلاق المنفذ.

### إعادة الاتصال

افصل الجهاز وأعد توصيله. يجب أن تعود نفس الهوية والدور وإصدار Hardware.

## المرحلة 3 — إعداد قابل للعكس

1. أنشئ Backup للإعدادات المرئية القابلة للاستعادة.
2. اختر قيمة منخفضة المخاطر وقابلة للعودة.
3. سجل القيمة الأصلية.
4. اكتب قيمة جديدة ضمن الحدود.
5. تحقق من القراءة الرجعية.
6. استعد Backup.
7. تحقق من عودة القيمة الأصلية بالقراءة الرجعية.

أي اختلاف في القراءة الرجعية هو `FAIL`، حتى لو قبل الجهاز أمر الكتابة.

## المرحلة 4 — الربط

1. نفذ Command Parameter الحقيقي على TX.
2. سجل إقرار الأمر وحده في اختبار TX.
3. ضع RX في وضع الربط وأرسل الأمر الحقيقي أو Legacy fallback المدعوم.
4. تحقق بصورة مستقلة من مؤشرات الطرفين وTelemetry أو دليل الرابط.
5. سجل نجاح RF فقط في اختبار **مشاهدة رابط RF من الطرفين**.

## المرحلة 5 — Firmware

### بناء الحزمة

معيار النجاح:

- Release وTarget والمنطقة التنظيمية محددة.
- طريقة الرفع مدعومة من Target.
- جميع القطاعات وعناوينها وبصمات SHA-256 ظاهرة.
- حزمة Recovery نزلت وحفظت خارج المتصفح.

### Bootloader

ادخل عبر الطريقة المطابقة للـTarget. يجب أن يظهر اسم الشريحة أو Target أو واجهة DFU الصحيحة قبل المسح.

### أول Flash طبيعي

- لا تقطع الطاقة عمدًا.
- راقب المسح والكتابة والتحقق.
- عند الفشل لا تكرر محاولات عشوائية؛ صدّر السجل أولًا.

### إعادة الإقلاع

لا تسجل `PASS` إلا بعد:

- عودة الجهاز عبر CRSF.
- تطابق Target أو استمرارية الهوية الموثقة.
- تطابق Release أو Commit المتوقع.
- القدرة على قراءة Parameters مجددًا.

## المرحلة 6 — Recovery

### استعادة عادية

نفذها على جهاز اختبار بعد نجاح Flash الطبيعي. تحقق من بصمة الحزمة وعودة Target والإصدار.

### انقطاع متعمد

اختياري وخطير. ينفذ في النهاية وعلى جهاز احتياطي فقط:

1. ابدأ الكتابة.
2. اقطع الاتصال في مرحلة `WRITING` المحددة.
3. أعد فتح التطبيق.
4. تحقق من ظهور `RECOVERY_REQUIRED`.
5. اختر نفس الجهاز وحزمة Recovery المطابقة.
6. نفذ الاستعادة.
7. تحقق من Target والإصدار بعد الإقلاع.

## قرار الجلسة

- `PASS`: الدليل المطلوب شوهد مباشرة.
- `FAIL`: العملية نفذت لكن النتيجة خالفت معيار القبول.
- `BLOCKED`: تعذر التنفيذ بسبب أداة أو كابل أو صلاحية أو Target غير متاح.
- `SKIPPED`: تجاوز مقصود ومبرر، خصوصًا اختبار الانقطاع المتعمد.
- `NOT_RUN`: لم يبدأ الاختبار.

لا يتحول المشروع إلى `HARDWARE_OBSERVED` بمجرد اكتمال السجل؛ يجب مراجعة الأدلة وربطها بالـCandidate SHA والجهاز المختبر.
